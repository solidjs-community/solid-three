## Drift (in both, but inconsistent)

### Canvas `gl` TypeScript interface block
- `canvas.mdx:42-48` and `README.md:133-140` show `gl?: Partial<WebGLRenderer> | readonly [..., Partial<WebGLRenderer>] | (canvas => ResolvedRenderer) | ResolvedRenderer`.
- Source `src/canvas.tsx:44-58` uses `Partial<Props<WebGLRenderer>>` (the solid-three `Props<>` wrapping that gives you array coercion, attach, events, etc.), not `Partial<WebGLRenderer>`. And the WebGL branches are gated on `WebGLRenderer extends ResolvedRenderer` (the lockout described in the prose under "Narrowing"). Update the TS block to reflect `Props<>` and the `extends ResolvedRenderer` conditional, or at least flag that the config-shorthand collapses to `never` when `Register` narrows.

### Canvas `camera` / `scene` / `raycaster` TS-block types are partial of the wrong shape
- `canvas.mdx:39` and `README.md:131`: `camera?: Partial<PerspectiveCamera | OrthographicCamera> | Camera`.
- Source `src/canvas.tsx:23`: `Partial<Props<PerspectiveCamera> | Props<OrthographicCamera>> | Camera` — i.e. `Props<>`-wrapped, not bare `Partial<Class>`. Same for `scene` (`Props<Scene>`) and `raycaster` (`Props<EventRaycaster>`).

### `useProps` Coercion table — order and rules
- `use-props.mdx:71-81` and the prose around it lists the rules. Compared to `src/props.ts:212-332` (`applyProp`):
  - **Event check**: docs put events as rule #3 (after dashed split). Source places event-detection (`isEventType`) AFTER the `NEEDS_UPDATE` flag toggle AND AFTER the `encoding → colorSpace` aliasing block. Practically irrelevant for behaviour (the prop is never both an event name and a needs-update key) but the documented order is wrong.
  - **Missing rule**: docs don't mention the `encoding`/`outputEncoding` → `colorSpace`/`outputColorSpace` aliasing (`src/props.ts:241-253`). Public, behaviour-affecting.
  - **Missing rule**: docs don't mention the auto-`colorSpace` assignment on assigned `Texture`s (`src/props.ts:301-321`). The user-visible effect is "textures pick up the renderer's outputColorSpace" — needs a line.
  - **Color rule misattributed**: docs row 6 says `source[key] is Color and value is string/number → set(value)`. Source has no Color-specific branch above the generic `setScalar` branch; the actual ordering is array → (setScalar if number AND not Color) → set(value) fallback. The Color string case (`color="red"`) lands in the generic `target.set(value)` line at `src/props.ts:291`, not a dedicated Color rule.
  - **`needsUpdate` finally block**: source unconditionally sets `source.needsUpdate = true` in the `finally` if the field exists (`src/props.ts:323-327`) — every prop set, not just the truthiness-flipped ones. Docs (`use-props.mdx:83`) say "After every assignment, if the target has a `needsUpdate` field, it's set to `true`" — that part matches; the `NEEDS_UPDATE` list explanation should clarify this list is what *additionally* flips `needsUpdate` on truthiness change *before* the assignment.
  - **`frameloop="demand"` requestRender** (`src/props.ts:328-330`): docs mention "if the renderer is on frameloop="demand", a render is requested" (`use-props.mdx:63`) — matches.

### `useProps` signature — `object` parameter name

- Source `src/props.ts:350`: parameter is named `accessor`, not `object`. Cosmetic but worth aligning.

### `useLoader` interface block — generic parameter naming
- Docs (`use-loader.mdx:28`, `README.md:647`): `UseLoaderOptions<TLoader, TResult>` with `onLoad?(resource: TResult)`.
- Source `src/hooks.ts:95-118`: `UseLoaderOptions<TLoader, TInput extends LoadInput<TLoader>>` and `onLoad?(resource: LoadOutput<TLoader, TInput>)`. Drift: the second generic is `TInput` (the URL input), not `TResult`; `onLoad` receives `LoadOutput<TLoader, TInput>`, not `TResult`.
- Also: `LoaderRegistry` interface block in `use-loader.mdx:110-122` and `README.md:735-747` shows `Loader<object, any>` and a phantom `Loader<TData, TUrl>` reference. Source (`src/data-structure/loader-cache.ts:16-40`) uses `Loader<any, any>`. The phantom `TData`/`TUrl` types in the `get` signature don't exist anywhere; that block won't typecheck as written.

### Raycasters update event type — missing `KeyboardEvent`?
- Source `src/raycasters.tsx:4`: `type RayEvent = PointerEvent | MouseEvent | WheelEvent`. Docs match (`raycasters.mdx:18`, README:827). ✓

### Events: docs claim `intersection: Intersection` always present
- `events/overview.mdx:42` says `intersection` is "Shorthand for `intersections[0]`" present for "events that raycast".
- Source `src/create-events.ts:74-76` only sets `event.intersection = intersections[0]` when `intersections` is passed. For `*Enter` and `*Leave` events, `intersections` IS passed (`src/create-events.ts:252, 325`). For `*Missed` events, `intersections` is not passed — correct per docs.

### `EventRaycaster.update` event type

The "When `update()` is called" list (`raycasters.mdx:28-30`, README:837) lists `click`, `mousedown`, `mouseup`, `mousemove`, `contextmenu`, `dblclick`, `pointerdown`, `pointerup`, `pointermove`, `wheel`. ### `useFrame` callback receives `context`, not bound-this

### Testing utilities exports — `test` vs `TestCanvas`
